## V2 — Enterprise Multi-User

### Overview

V2 transforms Adyton from a personal vault into a multi-user on-premise product. A single deployment serves an entire organisation (up to ~500 users), with personal vaults fully preserved and team group vaults layered on top. No vault content ever moves to a third-party server; everything remains self-hosted.

**Scope:** organisation tenant, group vaults, asymmetric key distribution, SSO plugins, backoffice admin UI, member suspension and revocation.

---

### Design Principles

1. **Personal vault is untouched.** The V1 ZK model (Argon2id → vault key → AES-256-GCM) remains exactly as designed. V2 adds a separate cryptographic layer for group vaults.
2. **SSO = authentication only.** SSO proves identity to the server. Vault unlock always requires a Vault PIN (the Argon2id input). SSO token ≠ vault key material.
3. **Server never sees group key plaintext.** Group keys are distributed via ECDH key wrapping. Server stores wrapped copies only.
4. **Admin can revoke group access, not personal vault content.** An admin who removes a member deletes their wrapped group key copies. The member's personal vault is unaffected and irrecoverable by anyone.

---

### Key Hierarchy — V2 Extension

```
Personal layer (V1, unchanged):
  master_password / vault_PIN
      └─ Argon2id → personal_vault_key
             └─ AES-256-GCM → personal vault entries

Group layer (V2, new):
  personal_vault_key
      └─ AES-256-GCM decrypt → user_ec_private_key  (X25519)
             └─ ECDH(user_private, ephemeral_public) → wrapping_key
                    └─ AES-256-GCM decrypt(wrapped_group_key) → group_key
                           └─ AES-256-GCM → group vault entries
```

**Key points:**
- `user_ec_private_key` is generated once at org onboarding and stored encrypted with `personal_vault_key`. The server never sees it in plaintext.
- `user_ec_public_key` is stored in plaintext on the server (it is public).
- `group_key` is a random 256-bit symmetric key generated by the group creator.
- Each group membership row stores one `wrapped_group_key` + the ephemeral public key used to derive the wrapping key.

---

### Group Key Wrapping (ECDH)

When user A adds user B to a group:

```
1. A fetches B's ec_public_key from the server.
2. A generates an ephemeral X25519 keypair (eph_priv, eph_pub).
3. shared_secret = X25519(eph_priv, B.ec_public_key)
4. wrapping_key  = HKDF-SHA256(shared_secret, salt=eph_pub, info="adyton-group-key-wrap-v1", len=32)
5. wrapped       = AES-256-GCM(group_key, wrapping_key)
6. Server stores: { group_id, user_id, wrapped_group_key, eph_pub, iv, auth_tag }
```

When B unlocks the group vault:

```
1. B decrypts personal_vault_key with vault_PIN.
2. B decrypts ec_private_key with personal_vault_key.
3. shared_secret = X25519(B.ec_private_key, eph_pub)   ← same shared_secret
4. wrapping_key  = HKDF-SHA256(shared_secret, ...) 
5. group_key     = AES-256-GCM-decrypt(wrapped_group_key, wrapping_key)
6. B decrypts group vault entries with group_key.
```

The server at no point holds any key in plaintext. The ECDH exchange is non-interactive (A does not need to be online when B unlocks).

### SSO Plugin Architecture

SSO is an **authentication plugin** — it does not change the vault crypto model. After SSO authentication the vault still requires a Vault PIN to unlock.

```
GET  /auth/sso                     ← list configured providers for the org
GET  /auth/sso/:provider/redirect  ← initiate OIDC/SAML flow
GET  /auth/sso/:provider/callback  ← OIDC callback (exchange code → tokens)
POST /auth/sso/:provider/saml      ← SAML assertion POST
```

All SSO paths converge on `AuthService.completeLogin()` — the same function used by email/password login. JWT issuance is identical. The only difference: SSO users have no Adyton password; their identity is verified externally.

**OIDC implementation:** `@nestjs/passport` + `passport-openidconnect`. Each org configures one OIDC provider (discovery URL + client credentials). Strategy is loaded dynamically per-request from the org's `SsoProvider` config. Supports Microsoft Entra ID, Google Workspace, Okta, Auth0, and any standards-compliant OIDC provider.

**SAML implementation:** `passport-saml`. Lower priority; add when a customer requires it.

**Vault PIN for SSO users:** SSO users set a Vault PIN at first login. The PIN is their Argon2id input — stored nowhere, same as a master password for email users. If a user loses their Vault PIN, their personal vault is irrecoverable (ZK invariant). Admin can re-enrol them into org groups by generating new wrapped group keys once they set a new Vault PIN.

### Backoffice — Admin UI

The backoffice lives at `/admin/**` inside the same Nuxt app, guarded by role (`owner` or `admin`). Regular members never see these routes. A separate `admin` layout provides distinct navigation.

```
/admin
├── /admin/members
│   ├── List all org members (role, status, last active)
│   ├── Invite by email (sends invite link)
│   ├── Change role
│   ├── Suspend / Reactivate
│   └── Kick (with optional group key rotation)
├── /admin/groups
│   ├── Create / rename / delete groups
│   ├── Manage membership (add/remove members)
│   └── View group metadata (entry count, last modified — not content)
├── /admin/sso
│   ├── Configure OIDC provider (discovery URL, client ID, secret)
│   ├── Test SSO flow
│   └── Require SSO for all members
├── /admin/security
│   ├── Require 2FA for all members
│   ├── Password policy (min entropy, breach check)
│   └── Session timeout policy
└── /admin/audit
    └── Audit log viewer (all VAULT_*, AUTH_*, MEMBER_* events)
```

**ZK in the backoffice:** admins see group metadata (name, entry count) but never entry content. The backoffice has no way to decrypt vault entries — it does not hold any vault key.

### Kick and Suspend

**Suspend (reversible):**
```
1. OrgMember.status = 'suspended'
2. All refresh tokens for the user revoked (immediate logout)
3. JWT issuance blocked: completeLogin() checks org membership status
4. WrappedGroupKey rows kept (fast reactivation)
5. SSO callback also blocked: org-membership check runs before JWT issuance
Reactivate: OrgMember.status = 'active' → user can log in again, group access restored
```

**Kick (destructive):**
```
1. OrgMember.status = 'kicked'
2. All refresh tokens revoked
3. WrappedGroupKey rows deleted for ALL org groups
4. Personal vault entry: untouched (ZK — admin cannot access it)
5. Optional: group key rotation (admin-triggered, not automatic)
Re-entry: requires a new invite + new WrappedGroupKey generation
```

**Group key rotation (post-kick):**
When a kicked member may have cached the group key, the group owner can trigger rotation:
```
1. Generate new group_key
2. Re-encrypt all group vault entries with new group_key (client-side)
3. Re-wrap new group_key for each remaining member
4. Atomic server update: new entries + new wrapped keys in one transaction
```
Rotation is expensive (O(entries × remaining_members)) and optional. It is meaningful only if the kicked user was active recently and may have a live vault session.

### Security Analysis

**What V2 preserves from V1:**
- Personal vault remains fully ZK. Admin cannot access personal vault entries.
- Vault key never transmitted. Vault PIN never stored.
- Group key never transmitted in plaintext.
- ECDH exchange is non-interactive and does not require the inviting admin to be trusted with the group key in the final cryptographic state.

**New attack surfaces introduced:**
- **EC private key at rest:** the user's `ec_private_key` is stored encrypted on the server, wrapped by `personal_vault_key`. A server compromise exposes encrypted private keys. Attack path: obtain DB + brute-force Vault PINs to unwrap private keys to decrypt group keys to decrypt group vault entries. Mitigation: Argon2id parameters remain load-bearing; strong Vault PINs are critical.
- **Group key wrapping chain on server:** all `WrappedGroupKey` rows are stored on the server. An attacker who decrypts one member's private key can decrypt their wrapped group key copies. This is a key escrow by design — acceptable for enterprise recovery semantics.
- **SSO provider as identity oracle:** if the OIDC provider is compromised, an attacker can authenticate as any org member. They still cannot decrypt vault contents without the Vault PIN. Mitigation: require 2FA in the org security policy; enforce 2FA at JWT issuance even after SSO.
- **Admin can revoke access but not read content:** org admins can kick members and delete their wrapped keys, but cannot decrypt group vault entries without being a group member themselves. This is an intentional capability boundary.

**What V2 explicitly does not provide:**
- Admin vault content recovery. A member who loses their Vault PIN loses their personal vault. An admin can re-enrol them to groups but cannot restore personal entries.
- Cross-instance group sharing. That is V3.

---

### Migration from V1

V1 deployments are single-user by definition. Migration to V2:

1. Deploy V2 image.
2. New migrations add `organisations`, `org_members`, `groups`, `group_memberships`, `wrapped_group_keys`, `user_key_pairs`, `sso_providers` tables.
3. Existing V1 user becomes the `owner` of a new Organisation row (auto-migration).
4. Personal vault entries are untouched — no re-encryption.
5. User generates their EC key pair on first post-upgrade login (client-side, pair stored encrypted).
6. Admin creates groups and invites other users.

V1 → V2 is non-destructive. A V2 deployment with one user is functionally identical to V1.
